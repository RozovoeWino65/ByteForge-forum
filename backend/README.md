# ByteForge API · локальный MVP

## Запуск на Windows

Из архива распакуйте **всю** папку `Workspace` (не открывайте файлы внутри ZIP). Нужна Java 11 или новее; для разработки рекомендуем JDK 21. Проверка: `java -version` и `javac -version`. В двух окнах PowerShell из корня репозитория `Workspace\ByteForge-forum`:

```powershell
# Окно 1: API. В архиве JAR уже собран.
cd backend
java -jar target/byteforge.jar
```

```powershell
# Окно 2: статический сервер фронтенда. Нужен Node.js с npm (рекомендуем Node 24).
cd frontend
npm start
```

Откройте **http://localhost:4173**. Альтернатива `npm start`, если установлен Python: `py -m http.server 4173 --bind 127.0.0.1` из каталога `frontend`. `npm start` при первом запуске скачивает `serve`. Файл `index.html` напрямую не открывайте. Остановить процессы — `Ctrl+C` в каждом окне.

## Как менять код

`backend/pom.xml` можно открыть как Maven-проект в IntelliJ IDEA. Maven отдельно не нужен: в каталоге `backend` есть wrapper для Windows и Linux/macOS. После правок остановите API и выполните:

```powershell
.\mvnw.cmd clean package
java -jar target/byteforge.jar
```

На Linux/macOS: `./mvnw clean package`, затем та же команда `java -jar`. Первая сборка требует интернета для загрузки Maven и библиотек. `package` компилирует исходники, запускает JUnit и собирает JAR с зависимостями. Только тесты — ` .\mvnw.cmd test`. Для автономных тестов фронтенда: `npm ci` и `npm test` в `frontend` под Node 24.

## Путь одного запроса

1. `frontend/js/api.js` отправляет JSON на `http://localhost:3000/api`. Режим `rest` уже выбран в `config.js`.
2. `Main.java` открывает файловую базу H2 и запускает HTTP-сервер только на loopback. `Api.java` выбирает маршрут, разбирает JSON через Gson, проверяет типы и длины полей. Для браузера разрешены `localhost:4173` и `127.0.0.1:4173`, включая предварительный `OPTIONS`.
3. `Store.java` выполняет параметризованные SQL-запросы через JDBC. При входе он ищет ник без учёта регистра, сохраняя исходное написание. Клиент получает случайный токен; в `sessions` хранится его SHA-256 и `user_id`.
4. При публикации `Api` проверяет Bearer-токен. `Store` записывает найденный `user_id`, а не имя из тела. Для ленты сервер соединяет `posts` с `users` и отдаёт имя автора строкой. Удаление ограничено условием `id = ? AND author_id = ?`.

| Маршрут относительно `/api` | Результат |
|---|---|
| `POST /auth/login` | 200: `{user, token}` |
| `GET /categories` | 200: пять категорий; `LEFT JOIN` и `COUNT(p.id)` дают 0 для пустых |
| `GET /posts` | 200: массив, новые сверху; опционально `?categoryId=tech` |
| `POST /posts` | 201: созданный пост; нужен Bearer |
| `DELETE /posts/:id` | 200: `{ok, id}`; нужен Bearer владельца |

Точные поля — в [`frontend/API.md`](../frontend/API.md). Ошибки приходят как `{ "message": "…" }` на русском: 401 — нужен вход, 403 — пост чужой, 404 — не найден, 422 — не прошла валидация.

## База и ограничения MVP

`src/main/resources/schema.sql` создаёт `users`, `categories`, `posts`, `sessions` и заполняет категории. При запуске **из `backend`** рабочая БД лежит в `backend/data/byteforge.mv.db`. Перезапуск не удаляет посты и сессии; для полного сброса остановите сервер, удалите `backend/data`, запустите и войдите заново. База и `target` исключены из Git.

Вход **без пароля**, как в контракте: любой, кто введёт существующий ник, получит новую сессию этого пользователя. Токены не истекают, выход на фронте очищает локальную сессию. Это учебный режим для локальной демонстрации, не публичная аутентификация.

## Что проверить перед коммитом

- Откройте http://localhost:3000/api/categories — при первом запуске пять категорий с нулевыми счётчиками; в `/api/posts` — `[]`. Мок-посты из браузера не переносятся.
- Войдите как `Богдан`, создайте пост в «Технологии» с текстом в две строки. Проверьте фильтр, счётчик и перенос строки после обновления страницы.
- В другом профиле браузера войдите под другим ником: пост виден, но не ваш. Вернитесь в первый профиль, удалите пост — счётчик уменьшится. Если на фронте осталась старая mock-сессия, выйдите и войдите снова.
- `src/test/java/ru/byteforge/ApiTest.java` проверяет эти правила по HTTP, включая прямой отказ `403`, подмену автора в JSON, повторный вход с другим регистром, preflight и сохранность после рестарта.
- В корне репозитория: `git status --short --branch`. Исходники бэкенда новые (до `git add` отображаются как `?? backend/`); JAR и рабочую БД добавлять не нужно.
